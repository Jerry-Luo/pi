main 的序厅：一切决策之前的环境收敛

控制流刚从 cli.ts 的 main(process.argv.slice(2)) 进入。在任何"产品决策"（模式分流、会话创建、UI）之前，main 的前 30 行先把进程环境收敛到位。本页只讲这一件事：packages/coding-agent/src/main.ts:569–597（1.1.0）。

速查 · 启动三层映射 · 使命 · 进度

01场景

你在终端敲下 pi（或 pi --print "hi"）。此刻进程已经具备什么？回顾 启动三层：setupCli() 已设好进程标题、两个环境标记、警告静音和初始 HTTP dispatcher，静态导入的各 chunk 也已完成模块初始化。

现在进入 main。接下来你会看到五件事依次发生：计时清零 → 主题校验器注册 → 扩展工厂合并 → 离线归一化 → 认证短路与不信任的自举配置。它们共同构成所有后续分支的"地板"。

02定向阅读 A —— 签名与四件小事

569–571 · MainOptions
整个可选配置只有一个字段：extensionFactories?: InlineExtension[]（类型来自 core/extensions/types.ts）。这是 SDK / 嵌入方的注入口——程序化调用 main 时可以不落盘地携带内联扩展工厂。终端用户永远不传它。
573 · 签名
args 是 cli.ts 里剥掉 node 与脚本路径后的用户参数；options 只服务于程序化调用者。
574 · resetTimings()
来自 core/timings.ts。清零启动计时表；后续会有 time("parseArgs")、time("createSessionManager") 等里程碑陆续记录，用于启动性能观测。
575–576 · 主题校验器
源码注释说明动机：命令（package/config）与启动选择器可能在 runtime 创建之前加载用户-authored 主题。把 validateThemeJson（modes/interactive/theme/theme-schema.ts）注册进主题系统（theme.ts 的 setThemeJsonValidator），任何代码在任何时刻加载主题 JSON 都会被 schema 校验——不需要等待交互式运行时存在。
577 · 扩展工厂合并
builtInExtensions（extensions/index.ts）在前、调用方注入在后，合成一个数组。这个数组之后会同时喂给 package/config 命令处理器和真正的会话创建——一处合并，处处使用。
578–582 · 离线归一化
离线 = CLI 旗标 --offline 或 环境变量 PI_OFFLINE 为真值（isTruthyEnvFlag）。一旦离线，就把两个环境变量写回进程环境：PI_OFFLINE="1" 与 PI_SKIP_VERSION_CHECK="1"。注意这个模式：CLI 旗标被归一化为环境变量，深处的代码（比如版本检查）只需要读 env，永远不需要接触 Args。

03定向阅读 B —— 认证短路与不信任的自举

584–586 · 认证短路
runAuthCommand(args)（main.ts:133）返回布尔值表达"是否接管了本次命令"：帮助、解析失败（置 exitCode=1）、成功执行认证子命令都返回 true；不是认证命令返回 false。返回 true 时 main 直接 return——不读设置、不建会话、不建 UI。因果：登录必须能在全新或半损坏的环境下工作（比如第一次 pi auth login 时全局设置文件还不存在），所以认证排在一切配置读取之前。
588–590 · Windows 专属清理
自更新在 Windows 上会因文件锁把旧文件挪进"隔离区"（utils/windows-self-update.ts）；下一次启动时用包目录（config.ts 的 getPackageDir）清理残留。
591 · cleanupManagedInstall()
来自 package-manager-cli.ts，无条件执行：清理受管安装（pi.dev 安装器体系）的簿记残留。
593–594 · 两个目录
cwd = 用户所在项目目录；agentDir = getAgentDir()（config.ts）即全局 ~/.pi/agent。全局与项目两个维度贯穿后面所有设置逻辑。
595–597 · 不信任的自举
这是本段最重要的三行。创建的 SettingsManager（core/settings-manager.ts）带着 projectTrusted: false——不信任当前项目。因此第 596 行 getGlobalSettings() 只读全局设置里的 httpProxy 并应用（core/http-dispatcher.ts 的 applyHttpProxySettings），随后第 597 行重新执行 configureHttpDispatcher()（与 setupCli 里那次同名，这次带上代理）。因果：项目信任的决策（可能弹窗询问用户）发生在更晚的阶段；在此之前绝不能让刚 clone 的陌生仓库通过项目设置文件指定代理、截获 provider 流量。这是"先全局、后项目"的信任分级。
边界 到这里为止：没有创建 Session、Agent 运行时或任何 UI；没有解析通用参数（parseArgs 在更后面）；HTTP dispatcher 被配置了两次（setupCli 一次、代理应用后一次），第二次才是带代理生效的那次。

04推理：为什么这一段叫"环境收敛"

行为保护什么
计时清零 + 主题校验器注册后续任何路径（哪怕一次性命令）都在可观测、可校验的环境中运行
扩展工厂合并为一处package/config 与会话创建用同一份扩展清单，不会分叉
旗标 → 环境变量归一化深层代码只读 env，不需要传递 Args
认证最先短路登录不依赖任何可能缺失/损坏的配置
projectTrusted: false 自举网络信任决策完成前，陌生项目无法注入代理

另外埋一个伏笔：本段确立了本课反复出现的布尔接管约定——runAuthCommand 返回 true 即"我处理了，main 请返回"。下一段的 handlePackageCommand、handleConfigCommand 沿用同一约定。
